# 第 0 条纪律：像游戏本身就有无障碍，不像外挂

> **状态**：0.2.7.0 起生效，优先级高于本仓库其余全部规则。
> **来源**：用户转述的指点原话 ——「你不要把 mod 写得跟外挂是的，要写得像游戏本身就有这个无障碍一样。」
> **解读**（用户给出，本文据此展开）：
> 1. 优先采用游戏自己的完全键盘控制接口，与游戏函数进行交互；
> 2. 如果不存在游戏完全键盘控制，就手动制造完全键盘控制或补全它；
> 3. 不要加入「导航模式」这一类的类似外挂的东西。
>
> 本文把这些话落成**可判定、可验收、可机械检查**的工程规则。
> 本仓库其它文档（README、`docs/无障碍补丁流水线.md`、逐作文档模板）与本文冲突时，**以本文为准**。

---

## 1. 一句话判据

补丁的交互形态必须让玩家觉得「**这游戏本来就有这个无障碍**」，
而不是「**我装了一个外挂，外挂带我操作游戏**」。

判据不是「代码写在哪一层」，也不是「功能全不全」，而是：
**玩家的每一次界面操作，走的是不是游戏自己的那条路。**

具体拆成七条，全部为「是」才算合规范（§5 是验收问法）：

1. **入口**：按键落在游戏自己的输入处理/键位/焦点机制上，不是补丁另开的一套；
2. **状态**：当前项由游戏自己的选中态（或游戏自己的状态字段）决定；
   补丁**不允许**维护一份与游戏并行的焦点索引；
3. **语义**：按键语义与游戏键位体系一致，**没有补丁专属的元操作**
   （「先按 Tab 进入操作模式」就是元操作）；
4. **可摘除**：关掉补丁，游戏行为、键位、画面**完全不变**；
5. **不添物**：画面上没有补丁新增的可见元素（覆盖层、提示条、自绘焦点框）；
6. **事件驱动与标签来源**：朗读由游戏自身事件触发（台词方法、选项生成、面板打开），
   不是补丁每帧扫屏幕「猜现在在哪个界面」；玩家听到的控件名 / 页面名必须来自游戏
   可见文本或本地化资源，对象名、注册名、资源名只进日志，不得当朗读标签。
7. **浏览 / 激活分离**：方向键、朗读、焦点移动只做「浏览」；购买、使用、确认、跳转、
   读档等**动作必须来自玩家的显式按键**，并由游戏自己的 Submit / Click / 动作函数执行 ——
   补丁不得因为「浏览到 / 读到了」就替玩家触发。

## 2. 为什么它排在第 0 条

技术栈路线（§3）决定「能不能做」，交互形态决定「做出来像什么」。
后者错了，前面所有工程纪律都白做：功能齐、证据齐、日志齐，
玩家一上手仍然觉得自己在用一个**游戏之外的辅助工具**。

现有 `UiNav` 的「导航模式」正是反例的标本：

| 导航模式的做法 | 为什么像外挂 |
|---|---|
| `Tab` 进入/退出一个「导航模式」 | 游戏里本来没有这个状态；玩家要先学补丁的元操作 |
| 每帧扫描 `Selectable`，自己排一份焦点表 | 与游戏的选中态并行；两个「当前项」可能不一致 |
| 导航模式里接管回车/空格并静音 uGUI submit | 改变了游戏输入语义；只有补丁在时才这样 |
| 未命名控件念「未命名按钮，第 N 项」 | 补丁在猜游戏界面；标签是补丁的推断而非游戏的事实 |
| 无控件模型时退回「临时编号菜单」 | 玩家在操作补丁的菜单，不是游戏的界面 |

这不是说「键盘操作」本身像外挂。**游戏自己提供的键盘操作是游戏的一部分**；
补丁要复用、补齐的是这一层。区别在于：
**补全缺失的游戏能力** ≠ **另造一套游戏没有的操作体系**。

## 3. 三条判定（对应解读 1 / 2 / 3）

每个作品在 **P0 可行性验证**阶段必须二选一定下结论，并写进逐作的
`docs/交互形态判定.md`；未写判定不得进入 P2 骨架、不得把导航模式当默认方案。
「补出来的键长什么样」由 `docs/操作逻辑公约.md` 统一（语义动作、激活分级、标签来源、
冲突与差异登记），本纪律只判形态对错；逐作差异填 `docs/操作约定.md`。

### A. 游戏已有「完全键盘控制」→ 直接复用，补丁只朗读

**判定条件**：玩家**不装补丁**也能只用键盘完成本作所有需要操作的事 ——
标题菜单、存读档、设置、画廊、选项、确认框、退出，一个界面都不能漏。
「完全」按**全流程**算，不是只测标题菜单。

**做法**：

- 补丁只做朗读：读游戏自己产生的文本与状态；
- **不碰输入、不碰焦点、不改键位**；所有按键原样交给游戏；
- 不拦截、不模拟、不加模式开关；
- 朗读必须由游戏自身事件触发；**不准靠扫屏判断界面**；
- 唯一允许的例外是「重读最近一句」「切换语音后端」这类**朗读侧**热键 ——
  它们不改变游戏的操作路径，且必须避开游戏原生键位（README 有专节）。

**证据**：P1 里给出「纯键盘走通全流程」的操作步骤与结果（录像/日志/逐步记录皆可）。
读代码推断「应该有键盘」不算证据。

### B. 游戏有键盘控制但不完全 → 在游戏自己的输入/焦点层补全

**判定条件**：游戏有部分键盘操作，但某些界面/操作只能鼠标，
或者键盘路径走不通（焦点不可见、没有选中态、确认框点不到）。

**做法**（按优先级）：

1. **先找游戏自己的入口**：键位表 / `Input.GetKeyDown` 所在方法 /
   `ISubmitHandler` / 按钮点击最终调用的方法 / 游戏自己的选中态字段。
   用 Harmony 在**游戏自己那条路径**上补缺失的键位或补一次调用。
2. **补出来的键符合游戏自己的键位习惯**：同一界面里不与已有键冲突；
   全局热键不抢占游戏键；优先沿用游戏已有的确认/取消键语义。
3. **焦点/选中态用游戏自己的机制**（`SetSelectedGameObject` 或游戏自己的
   hover/selected 字段），让视觉高亮、音效、动画照常 —— 因为那就是游戏自己的反馈。
4. **没有模式开关**：进入一个界面，键盘就是能操作；不需要先按某个键
   「进入操作状态」，也不需要记得「现在是导航模式还是剧情模式」。
5. 若某界面确实补不全，**如实登记**为感知/操作缺口（§5 第 7 问），
   不许用一个通用扫描引擎假装它被覆盖了。
6. **新增按键前先查四项冲突**：游戏原生键位表 / 输入映射、Steam 等平台快捷键
   （`F12` 是截图，禁用）、读屏器常用组合键、输入法 / 系统占用。查不出结论就
   登记为未知，不许「先加上试试」。

**证据**：补丁去掉后该界面恢复原状；装上后键盘路径与游戏原生键盘路径**同形**
（同一套焦点、同一套按键语义）。

### C. 游戏没有键盘控制/没有控件模型 → 制造完全键盘控制，但它必须仍是「游戏的一部分」

**判定条件**：UI Toolkit / 自绘界面 / 无 `Selectable` / KiriKiri Z 这类没有
控件模型的界面。

**做法**（按优先级）：

1. **找游戏自己的动作入口**：鼠标点击最终调用的方法、按钮的 `onClick` 目标、
   选项选择函数、界面切换函数。**直接调用/触发这些函数**，
   而不是用 `SendInput` / `PostMessage` / 鼠标坐标模拟点击。
2. **尽量借用游戏自己的焦点/选中数据**；没有就维持一个**最小**的选中表示，
   但**不新建一套 UI 层**：不画 overlay、不弹补丁菜单、不显示「导航中」。
3. **不引入模式开关**。若必须在「操作界面」与「推进剧情」之间分流，
   用**上下文自然分流**（例：界面上有可操作项时，方向键移动、回车确认；
   没有时回车推进剧情），而不是让玩家按 Tab 切换状态。
   上下文分流与模式开关的区别：前者玩家无需学习，后者需要先学一步元操作。
4. 如果确实做不到「无模式」，必须在逐作 `docs/交互形态判定.md` 与发布说明里
   **明确记为遗留缺陷**并解释原因；**不允许**把它当成框架的默认方案。
5. **临时编号菜单**只有在「没有任何可调用入口、只能读出屏幕上的选项」时使用，
   且必须标注为**过渡**，不得成为框架默认；一旦找到游戏自己的入口就替换掉。

**证据**：每个界面的「操作入口」都要有反编译实查的方法名或探针事实；
「没实测」不许写成「已补全」。

### A/B/C 共同的收尾纪律（补全输入时尤其重要）

1. **焦点恢复只走游戏自己的生命周期**：在目标界面打开 / 关闭的原生事件里恢复，
   不用轮询、不用固定延时、不在销毁 / 退出过程中抢焦点，也不越过当前模态
   （如确认框）去抢。
2. **延迟朗读必须绑定真实事件且可取消**：不写死「等 N 秒」「第 N 步」；
   界面关闭 / 切换 / 退出时取消尚未播出的条目，避免旧界面内容串到新界面。
3. **补丁加的东西要能干净撤销**：输入屏蔽、事件订阅、焦点恢复、临时选中态
   都在销毁 / 退出时撤销；`EventSystem` 已销毁后不得再操作焦点。

## 4. 反模式清单（「外挂味」自查表）

逐条对照；命中任何一条，必须给出理由并登记，不能默默存在。

| # | 反模式 | 为什么像外挂 | 合规范做法 |
|---|---|---|---|
| X1 | 用热键进入/退出的「导航模式」「焦点模式」「浏览模式」 | 游戏本来没有这个状态，玩家先学补丁 | 无模式；键盘直接可用 |
| X2 | 补丁自己扫屏、自己维护焦点列表 | 与游戏选中态并行，两个「当前项」 | 用游戏自己的选中态 |
| X3 | 拦截/静音游戏 submit、改 `sendNavigationEvents` 来适配补丁 | 改变游戏输入语义 | 仅在修复游戏对读屏的缺陷时最小改，且必须逐作判定（README 专节） |
| X4 | 每帧扫 UI「猜」当前界面/当前台词 | 补丁在猜游戏状态 | 读游戏自己的事件与字段 |
| X5 | 补丁自绘覆盖层、提示条、焦点框、补丁菜单 | 画面上出现游戏没有的东西 | 不添可见元素；朗读即输出 |
| X6 | 合成输入（`SendInput`/`PostMessage`/鼠标坐标）代替调用游戏函数 | 绕过游戏自己的校验与分支 | 调游戏自己的动作函数 |
| X7 | 让玩家记编号/背键位来完成界面操作 | 把无障碍变成补丁的操作系统 | 界面键位符合游戏习惯 |
| X8 | 全局读键无焦点门、作为唯一入口 | 影响游戏外，像外挂/宏 | 仅窗口无焦点时兜底，默认关 + 焦点门 |
| X9 | 把「界面导航」当新作出厂默认配置 | 默认形态就在宣告「这是补丁功能」 | 新作默认不启用；先做 A/B/C 判定 |

> **X3 不是绝对禁止**：若游戏完全不用选中态，不修 `sendNavigationEvents`
> 会让鼠标点过的按钮在按空格推进剧情时被重复点击 —— 那是**修复游戏的读屏缺陷**，
> 不是加功能。判据仍是「关掉补丁后游戏行为不变」，且必须逐作判定。

## 5. 验收标准（写进逐作测试问卷第 2 节）

1. **不按任何补丁专属模式键**，能否只用键盘走完本作主流程？
2. 每个界面里，键盘的「当前项」是否就是游戏自己的选中项
   （视觉高亮 / 音效在哪，朗读就在哪）？浏览是否只读、动作是否都来自玩家的显式按键？
3. 关掉补丁，游戏键位与行为是否完全不变？
4. 补丁有没有新增画面上看得见的东西？
5. 补丁有没有让玩家背一套游戏里不存在的操作？
6. 朗读是否由游戏事件触发（而不是补丁扫描推断）？
7. 以上任一为「否」时，是否已在文档中如实登记为遗留缺陷？

前 6 条全「是」= A/B/C 任一路线均合格；第 7 条为「是」= 允许带缺陷发布，
但必须让玩家知道。**没有第 7 条，缺陷就会变成谎言。**

## 6. 与既有红线的关系

- **红线 1（不扩大可达范围）**：形态纪律是它的前提。外挂形态常伴随扩大可达
  （扫到隐藏控件、激活不可用项）；但即使没有扩大，形态本身也不合格。
- **红线 2（关掉补丁游戏行为不变）**：形态纪律的机械检验，测试问卷第 8 节。
- **新增红线 3**：**不得把「导航模式」作为新作的默认交互形态**（细则就是本节；
  §7 是遗留与过渡条款，不是红线本身）。

## 7. 遗留与过渡条款（诚实条款）

- `UiNav` 的导航模式是 0.2.x 的历史实现，**不是**本纪律的合规范本。
  它存在的原因是当时的作品没有更好的入口，且已发布、玩家在用。
- **新作**：默认**不得**启用导航模式；必须先在 P0 完成 §3 的 A/B/C 判定，
  写进 `docs/交互形态判定.md`，再决定实现方式。
- **旧作**：不强制回改；任何对旧作的实质性界面改造，优先按本纪律迁移。
- 判定为 C 且确实无法避免模式开关时：必须在交付文档里写明
  「这是遗留形态，不是推荐做法」，并在 CHANGELOG 记录原因与范围。
- 本仓库的 `A11yHost` / `UiNav` 保留旧字段与旧行为，是为了**老作逐字节不变**；
  保留不等于推荐。「只增不改」与「新作默认」是两件事。

## 8. 证据与文档要求

- **判定必须落到文件**：逐作仓 `docs/交互形态判定.md`，随版本更新；
  只在聊天/提交信息里说，等于没判定。
- **A 类证据**：不装补丁的「纯键盘全流程」记录（步骤 + 结果）。
- **B/C 类证据**：游戏自身入口的反编译实查（方法名/类型名），
  以及「补丁关掉后行为恢复」的对照。
- **判定是实测结论，不是读代码猜的**：P0 阶段就要给出操作步骤与结果；
  P1 探针负责把「游戏自己的输入/焦点入口」查实。
- **证据分级**：读代码 / 反编译摘要 < 资源与配置 < 运行日志 / 探针转储 < 实机操作。
  每条结论标注等级；只有实机操作能写「已验证」，其余写「据…推断」「尚未实测」。
- **STOP**：同一现象出现两种解释、补丁行为无法用已查证据解释、与既有结论矛盾、
  关键入口找不到时，停止继续写代码，把 unknowns 记进逐作文档并询问；
  STOP 只停相关模块，不阻塞独立模块。
- 与「三条铁律」的关系：本纪律的每一条判定同样受
  「不许猜」「不许把没实测说成已验证」「每条依据可追溯」约束。

## 9. 常见误读

| 误读 | 纠正 |
|---|---|
| 「键盘操作就是无障碍，有键盘就合规」 | 有键盘但不走游戏自己的路径，仍然是补丁的操作系统 |
| 「游戏没有焦点，只能扫屏 + 模式开关」 | 先找游戏自己的动作函数（C 类第 1 条）；扫屏是最后手段且要登记 |
| 「模式开关对玩家更方便」 | 方便的是补丁作者；玩家的成本是每个界面先学一步元操作 |
| 「补丁自己画个界面更清楚」 | 画面上多出游戏没有的东西，正是「像外挂」的直观来源 |
| 「老作用着挺好，说明导航模式没问题」 | 老作是遗留豁免（§7）；新作默认必须按本纪律判定 |
| 「这是框架，不是具体作品，可以不管形态」 | 框架的模板与默认值决定了下一个作品像什么；纪律必须写进模板 |
